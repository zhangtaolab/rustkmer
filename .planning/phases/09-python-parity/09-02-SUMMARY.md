# Phase 9 Plan 02: Single-Sort GIL-Released `save_database` and Cross-Surface Byte Identity Summary

`PyCounter.save_database` now snapshots the counter, sorts the pairs exactly once with `rayon::par_sort_unstable_by_key` inside `py.detach`, and writes through the new `RKDatabase::from_sorted_kmer_pairs` — proving Python (t1/default) and CLI (t1/t4/default) emit the same `a5da813e…` golden bytes.

## What Was Built

### Task 1: Sorted-input constructor as a proven pure addition

- `src/database/format.rs`: added `RKDatabase::from_sorted_kmer_pairs(kmer_pairs, kmer_size, canonical)` immediately after `from_kmer_pairs`. It imports the pairs as `KmerEntry` values in caller order, sets `sorted: true`, and performs **no sort**. The header literal is identical to `from_kmer_pairs` (`data_offset: 42`, `index_offset: 0`, `total_kmers` == `entries.len()` per IN-03). A `debug_assert!` documents the caller-proven-order contract and panics on descending input in debug builds.
- Pure-addition proof: `git diff --numstat -- src/database/format.rs` = `78  0  src/database/format.rs`; `git diff -U0` contains zero removed lines. Pre blob `eb0d5bf2…` (re-verified from `HEAD:src/database/format.rs`), post blob `dedfd95a475c745c029f164e2a99fb150c665582`.
- Untouched by a single byte: `from_kmer_pairs`, `DatabaseHeader::write_to`, `KmerEntry::write_to` / `read_from`, `RKDatabase::write_to`.
- `tests/sorted_pairs_constructor_tests.rs` (5 tests): byte equality against `from_kmer_pairs(.., sorted=true)` both in memory and through `TempDir` files; empty input is a 42-byte header-only file with `sorted == true`; one entry round-trips with record count 1; the k21/canonical golden input reproduces `a5da813e…` and equals the committed fixture byte-for-byte; descending input panics under `#[cfg(debug_assertions)]`.
- `evidence/format_rs_blob_audit.json`: generated by a validating `python3 -c` script that refuses to write on an unchanged blob, any numstat deletion, any removed diff line, a dirty `tests/fixtures/`, or a command outside the three it executed. It records pre/post blobs, the pure-addition proof, the three green suites, a `later_verification` cross-reference to `rkdb_v2_byte_identity_tests` / `output_pipeline_tests`, and the explicitly scoped Phase 8 supersession.

### Task 2: One sort, GIL released, bytes unchanged

- `pyo3/src/counter.rs`: `save_database(&self, py: Python<'_>, file_path: &Bound<'_, PyString>) -> PyResult<()>` keeps its Python-visible signature, extracts `path_str: String` and a cloned `Arc<RustPyCounter>` before the release, and runs `py.detach(move || save_database_on_counter(&counter, &path_str))`.
- New private `enum SaveDatabaseError { Empty, Database(String), CreateFile(String), Write(String) }` with `Display` reproducing the four verbatim messages: `Cannot save empty database. Add k-mers first.`, `Failed to create database: {e}`, `Failed to create file: {e}`, `Failed to write database: {e}`.
- `save_database_on_counter`: snapshot via `get_all_counts`, `Empty` on no pairs, one `par_sort_unstable_by_key(|&(kmer, _)| kmer)`, `RKDatabase::from_sorted_kmer_pairs`, `File::create` → `BufWriter`, `db.write_to`, explicit `flush`. The `DatabaseHeader::new` local and the `DatabaseHeader` import are gone; no `unwrap`/`expect`.
- `pyo3/tests/test_save_database_byte_identity.py` (8 tests): fresh-interpreter Python arms (`threads=1`, `threads=None`) and CLI arms (`--threads 1`, `--threads 4`, default) all hash to `a5da813e…` and to `tests/fixtures/golden_k21_canon_sorted.rkdb`; an explicit 1-vs-N test collects all five arm hashes into one set; the empty-counter `ValueError` and the directory-target `Failed to create file` `ValueError` are re-asserted. Skips are build-infra only (missing release binary or fixture).
