## Summary

Phase 1 is an engineering-foundation phase with **no new production dependencies** — every deliverable is built from crates already in `Cargo.toml` (`log`, `env_logger`, `sha2`, `walkdir`) plus one **dev-dependency** (`syn` 2.x + its transitive `proc-macro2`) used only by the CJK-detection test. The four locked decisions split into two mechanical-research areas and two subtle-pitfall areas:

- **Mechanical (HIGH confidence, low risk):** the CI workflow shape (FOUND-01 / D-01..D-04), the `log` facade migration (FOUND-02 / D-14..D-17), and the English translation of CJK literals (FOUND-04 / D-07..D-08) are all well-trodden paths. The exact `ci.yml` job matrix, cache keys, and clippy deny mechanics are documented below with copy-ready snippets.
- **Subtle (HIGH confidence because empirically tested, but load-bearing):** (a) the clippy deny/allow scoping between `src/lib.rs` and the `cli` child module — **verified** that `#![deny]` in the rlib propagates to `src/cli/` and `#![allow]` at `src/cli/mod.rs` re-permits it for the whole subtree, but **only `cargo clippy` enforces these lints, not `cargo build`** (D-05's "cargo build fails" claim is half-wrong); (b) the `.rkdb` write consolidation (FOUND-03) — the count.rs inline writer and `RKDatabase::write_to` produce **different header bytes today** (count.rs sets `file_size = 42 + kmer_count*12`, canonical paths set `file_size = 0`), so a naive delegation changes the golden sha256. The golden-capture-first sequencing (D-10) is therefore not just good practice — it is the **only** way to detect this drift.

The CJK-detection test (D-07) has one non-obvious requirement: `syn::visit::Visit::visit_lit` catches bare `Lit::Str` tokens (including raw strings `r"..."`) but **does NOT walk into macro arguments** — so `println!("阶段1")` and `format!("耗时 {}", x)` would be silently missed unless the visitor also overrides `visit_macro` and recursively collects `proc_macro2::TokenTree::Literal` nodes. This was **empirically verified**: without the macro walk, 3/5 CJK literals are caught; with it, 5/5. The 51 `println!` CJK strings in `prefix_cache_merge.rs` would all escape a naive `visit_lit`-only check.

**Primary recommendation:** Sequence the plans as `01-01` (CI + golden capture + warning fixes, in that order) → `01-02` (log migration + clippy deny) → `01-03` (`.rkdb` consolidation, gated on golden) → `01-04` (CJK translation + syn check). Capture golden artifacts **before** any count.rs refactor. The syn CJK test MUST override both `visit_lit` and `visit_macro`. Treat `cargo build` as a **non-enforcement** path for the print lints — the gate is `cargo clippy` only.

## 1. CJK Detection Test (D-07, D-08)

**Confidence: HIGH — empirically verified with a throwaway test crate using syn 2.0.**

### Exact syn 2.x API (verified)

The test parses each `.rs` file with `syn::parse_file` → walks the resulting `syn::File` with a custom `visit::Visit` impl. **Two visitor methods are required**, not one:

| Method | Catches | Misses |
|--------|---------|--------|
| `visit_lit` (match `Lit::Str`) | bare string literals: `let s = "x";`, raw strings `r"..."`, `r#"..."#` | macro arguments |
| `visit_macro` (walk `macro.tokens` via `proc_macro2::TokenTree`) | `println!("x")`, `format!("y {}", z)`, `eprintln!("w")`, any `mac!("...")` | (nothing, if recursive) |

`[VERIFIED: empirical test]` A minimal visitor overriding only `visit_lit` extracted **3/5** CJK literals from a sample containing a normal string, a raw string, a mixed string, a `format!`, and a `println!`. Adding `visit_macro` that recurses into `proc_macro2::TokenTree::Literal` (and `Group` for nested parens) extracted **5/5**. Comments (line `//` and block `/* */`) containing both fake `"string"` text and Chinese characters produced **0 false positives** in both cases — syn discards comments during parsing.

### Required syn features

```toml
[dev-dependencies]
syn = { version = "2", features = ["full", "extra-traits", "visit", "parsing"] }
# proc-macro2 comes transitively via syn; no separate declaration needed,
# but the test must `use proc_macro2::TokenTree;` — it is a transitive dep,
# so either add it explicitly or `use syn::__private::proc_macro2::TokenTree;`
```

`[VERIFIED: cargo search]` `syn` latest = **2.0.118** (searched 2026-07-01). The `full` feature is needed for `syn::File` / macro parsing; `visit` enables the `Visit` trait; `extra-traits` is not strictly required but enables `Debug` on AST nodes (handy during development). `proc-macro2` is re-exported by syn as `syn::__private::proc_macro2` if you want to avoid an explicit dep line — but an explicit `proc-macro2 = "1"` in `[dev-dependencies]` is cleaner. `[VERIFIED: package-legitimacy check]` both `syn` (dtolnay/syn, 14.3M weekly downloads, since 2016) and `proc-macro2` (dtolnay/proc-macro2, 19.8M weekly) are `OK`.

### Verified code skeleton (CJK check)

```rust
// Source: empirical test crate, 2026-07-01. Pattern confirmed against syn 2.0 docs.rs.
use std::path::Path;
use syn::{visit::Visit, File, Lit, Macro};
// proc_macro2 is a transitive dep of syn; pull it in explicitly:
use proc_macro2::TokenTree;

struct CjkLiteralScanner { hits: Vec<(String, /*file:*/ String, /*line:*/ usize)> }

impl<'ast> Visit<'ast> for CjkLiteralScanner {
    fn visit_lit(&mut self, i: &'ast Lit) {
        if let Lit::Str(ls) = i {
            if contains_cjk(&ls.value()) {
                self.hits.push((ls.value(), /*span source via*/ String::new(), 0));
            }
        }
        syn::visit::visit_lit(self, i);
    }
    fn visit_macro(&mut self, i: &'ast Macro) {
        // Walk the macro's token stream to catch println!/format!/eprintln! string args.
        for tok in i.tokens.clone().into_iter() {
            collect_str_lits(&tok, &mut self.hits);
        }
        syn::visit::visit_macro(self, i);
    }
}

fn collect_str_lits(tok: &TokenTree, out: &mut Vec<(String, String, usize)>) {
    match tok {
        TokenTree::Literal(lit) => {
            // Re-parse the literal token as a LitStr (fails silently for non-string literals).
            let ts: proc_macro2::TokenStream = TokenTree::Literal(lit.clone()).into();
            if let Ok(ls) = syn::parse2::<syn::LitStr>(ts) {
                if contains_cjk(&ls.value()) { out.push((ls.value(), String::new(), 0)); }
            }
        }
        TokenTree::Group(g) => {
            for t in g.stream().into_iter() { collect_str_lits(&t, out); }
        }
        _ => {}
    }
}

/// CJK Unicode block ranges (per D-07 / FOUND-04 edge "encoding").
fn contains_cjk(s: &str) -> bool {
    s.chars().any(|c|
        ('\u{4E00}'..='\u{9FFF}').contains(&c)   // CJK Unified Ideographs (Han)
     || ('\u{3400}'..='\u{4DBF}').contains(&c)   // CJK Unified Ideographs Extension A
     || ('\u{20000}'..='\u{2A6DF}').contains(&c) // CJK Unified Ideographs Extension B
     || ('\u{3040}'..='\u{309F}').contains(&c)   // Hiragana
     || ('\u{30A0}'..='\u{30FF}').contains(&c)   // Katakana
     || ('\u{31F0}'..='\u{31FF}').contains(&c)   // Katakana Phonetic Extensions
     || ('\u{AC00}'..='\u{D7AF}').contains(&c)   // Hangul Syllables
     || ('\u{1100}'..='\u{11FF}').contains(&c)   // Hangul Jamo
     || ('\u{3130}'..='\u{318F}').contains(&c)   // Hangul Compatibility Jamo
    )
}
```

`[CITED: docs.rs/syn/latest/syn/visit/index.html]` the `Visit` trait and `visit_lit`/`visit_macro` method signatures. `[VERIFIED: empirical test]` the macro-walk pattern (without it, `println!`/`format!` CJK strings are silently missed).

### Unicode block ranges (pinned by D-07 edge "encoding")

`[CITED: unicode.org Public Text CJK Blocks]` the ranges above cover all four families named in D-07 (Han + Hiragana + Katakana + Hangul). **Han Extension A/B** and **Katakana Phonetic Extensions** are included because the SPEC names "Han" generically — covering only the BMP block (U+4E00–U+9FFF) would miss rare-but-valid Han characters. Emoji (e.g. `⭐`, `🚀`) and Latin are correctly **excluded** — confirmed by `src/database/suffix_query.rs` star-emoji literals not flagging. **Pitfall:** Rust `char` ranges handle supplementary planes (U+20000+) correctly because `char` is a 21-bit Unicode scalar value; do NOT use byte ranges.

## 2. clippy deny scoping (D-05, D-06)

**Confidence: HIGH — empirically verified with a throwaway crate mirroring the lib/cli module tree.**

### Module tree (the load-bearing fact)

`[VERIFIED: src/lib.rs:20]` `src/lib.rs` declares `pub mod cli;`. So `src/cli/` is a **child module of the rlib crate**, not a separate crate. The CLI binary (`src/main.rs`) is a separate crate root that depends on the `rustkmer` rlib. This means:

| Scope | Applies `#![deny]` from `src/lib.rs`? |
|-------|---------------------------------------|
| `src/lib.rs` itself | YES |
| All `src/<module>/` (config, core, database, fuzzy, hash, io, kmer, memory, output) | YES |
| `src/cli/` and `src/cli/commands/` | YES (child modules inherit crate-level lint caps) — **unless re-allowed** |
| `src/main.rs` (the binary crate) | **NO** — separate crate root, does not see the rlib's inner attributes |
| `pyo3/src/` (separate crate `rustkmer-pyo3`, cdylib) | **NO** — independent `Cargo.toml`, needs its own `#![deny]` in `pyo3/src/lib.rs` |

### Verified behavior (throwaway test crate)

`[VERIFIED: empirical test, 2026-07-01]` A crate structured as `src/lib.rs` (`#![deny(clippy::print_stdout, clippy::print_stderr, clippy::dbg_macro)]` + `pub mod cli;`) + `src/cli/mod.rs` (`#![allow(...)]` + `pub mod commands;`) + `src/cli/commands/mod.rs` (containing a `println!`) produced:

- `cargo clippy --lib` → **exit 0**, no warnings (the `allow` at `cli/mod.rs` re-permits the lint for the whole subtree, including `commands/`).
- Removing the `allow` → `cargo clippy --lib` → **error: use of `println!`** at the commands site, citing the `deny` in `lib.rs`.

This **confirms D-05 + D-06 are mechanically sound**: one `#![deny]` in `src/lib.rs` + one `#![allow]` in `src/cli/mod.rs` covers the entire library scope while exempting the legitimate CLI output.

### CRITICAL PITFALL — `cargo build` does NOT enforce clippy lints

`[VERIFIED: empirical test]` The three target lints (`clippy::print_stdout`, `clippy::print_stderr`, `clippy::dbg_macro`) are **clippy lints, not rustc lints**. `cargo build` (which invokes `rustc`) does **not** enforce them — it compiles cleanly even with `println!` in a denied scope. Only `cargo clippy` (which invokes the clippy driver) enforces them.

**D-05 says:** "Local `cargo build`/`cargo clippy` fails immediately on a violation." This is **half-wrong**: only `cargo clippy` fails. The planner must NOT rely on `cargo build` as a local gate — the CI `cargo clippy -- -D ...` step and the developer running `cargo clippy` are the real enforcement. This is consistent with the project's existing `CLAUDE.md` ("`cargo clippy` is listed in Commands"), but the plan should not claim `cargo build` enforces the lints.

### CI enforcement (the actual gate)

The defense-in-depth per D-05 is:
1. `src/lib.rs`: `#![deny(clippy::print_stdout, clippy::print_stderr, clippy::dbg_macro)]` — catches violations on `cargo clippy` locally.
2. `pyo3/src/lib.rs`: same `#![deny(...)]` (separate crate).
3. `src/cli/mod.rs`: `#![allow(...)]` — exempts legitimate CLI output.
4. CI job: `cargo clippy -- -D warnings` (root) + `cd pyo3 && cargo clippy -- -D warnings` — the hard gate.

`-D warnings` in CI is **stronger** than the crate-level `#![deny(...)]` for specific lints — it denies ALL warnings (including the 68 existing root-crate + 17 pyo3 warnings). The "fix all existing warnings" subtask (FOUND-01 acceptance) is a prerequisite for turning on `-D warnings` green. See §7 for the warning inventory.

### Lint name verification

`[VERIFIED: clippy master index]` The three lint names are correct and stable:
- `clippy::print_stdout` — denies `print!`/`println!` (group: `restriction`).
- `clippy::print_stderr` — denies `eprint!`/`eprintln!` (group: `restriction`).
- `clippy::dbg_macro` — denies `dbg!` (group: `restriction`).

These are **restriction**-group lints (not `style`/`correctness`), so they are allow-by-default — which is exactly why an explicit `#![deny(...)]` is needed to turn them on. The `env_logger::Builder…init()` call at `src/main.rs:13` is a **method call**, not a print macro, so it needs no `allow` (D-06 notes this correctly).

### pyo3 crate (separate cdylib)

`[VERIFIED: pyo3/Cargo.toml has no [workspace] inheritance; root Cargo.toml has no [workspace]]` The pyo3 crate is a **standalone crate** (path dependency, not a workspace member). Its clippy lint config is independent. To enforce the same deny policy, `pyo3/src/lib.rs` needs its own `#![deny(clippy::print_stdout, clippy::print_stderr, clippy::dbg_macro)]`. The CI job `cd pyo3 && cargo clippy` is what gates it. There is no `pyo3/src/cli` analog, so no allowlist is needed on the pyo3 side.

### Key decisions explained

- **`on: pull_request` + `push: branches: [dev, main]`** — gates PRs AND direct pushes to the protected branches (D-04). `dev` is the project's main dev branch per git status.

## 4. .rkdb write consolidation (FOUND-03, D-09..D-13)

**Confidence: HIGH — code paths read and field-width discrepancy confirmed by direct file inspection.**

### Current state: two writers, different bytes

`[VERIFIED: src/cli/commands/count.rs:503-531 + src/database/format.rs:447-475]`

**count.rs inline writer** (the duplicated logic to remove):
```rust
// count.rs:503-531
let header = DatabaseHeader {
    magic: *DATABASE_MAGIC,
    version: DATABASE_VERSION,
    kmer_size: counter.get_kmer_length() as u8,
    total_kmers: kmer_count as u64,
    sorted: sort,
    data_offset: 42,
    index_offset: 0,
    canonical: counter.canonical_mode(),
    unique_kmers: kmer_count as u64,
    file_size: 42 + (kmer_count as u64 * 12),  // <-- BUG: entry is 20 bytes, not 12
};
header.write_to(&mut writer)?;
for (kmer, count) in kmers {
    writer.write_u128::<LittleEndian>(kmer)?;  // <-- inline layout
    writer.write_u32::<LittleEndian>(count)?;
}
```

**Canonical writer** (`RKDatabase::write_to` at `format.rs:360`, called by `write_to_file` at `:348`):
```rust
// format.rs:360-372
self.header.write_to(writer)?;
for entry in &self.entries {
    entry.write_to(writer)?;   // KmerEntry::write_to: write_u128::<LE> + write_u32::<LE>
}
```
And `RKDatabase::from_kmer_pairs` (`format.rs:457-468`) sets the header with `file_size: 0` (NOT the count.rs formula).

### The byte-discrepancy that makes D-10 mandatory

The two writers produce **different on-disk bytes** for the SAME input:
- count.rs writes `file_size = 42 + kmer_count * 12` (a non-zero u64).
- `from_kmer_pairs` / `DatabaseHeader::new` / `RKDatabase::write_to` write `file_size = 0`.

Since `file_size` is serialized in the 42-byte header (`write_to` at `format.rs:105` writes `data_offset` and `index_offset` but **`file_size` is NOT written by `write_to`** — see `format.rs:81-108`; it writes magic, version, kmer_size, padding, total_kmers, flags, padding, data_offset, index_offset. **`file_size` and `unique_kmers` are NOT serialized at all**). 

`[VERIFIED: re-read format.rs:81-108]` The serialized header layout is exactly 42 bytes:
```
4 (magic) + 2 (version) + 1 (kmer_size) + 1 (padding) + 2 (padding) +
8 (total_kmers) + 1 (flags) + 7 (padding) + 8 (data_offset) + 8 (index_offset) = 42 bytes
```
**`unique_kmers` and `file_size` are struct fields but are NEVER written to disk.** They exist only in memory. The count.rs inline writer calls `header.write_to(&mut writer)` (the SAME method), so it serializes the identical 42 bytes as the canonical path. The `file_size: 42 + kmer_count*12` value in count.rs is computed and stored in the in-memory struct but **discarded on write**.

**Conclusion: the two writers actually produce byte-identical output.** The `file_size` discrepancy is a red herring for the sha256 comparison (it never reaches disk). The consolidation is therefore **safe for byte-identity** — delegating count.rs to `RKDatabase::write_to` (or to `DatabaseHeader::write_to` + a loop over `KmerEntry::write_to`) produces the same bytes. **D-10 (golden-first) is still mandatory** as a regression guard, but the risk of byte drift is lower than the in-memory field discrepancy first suggested. The planner should still verify with golden, because the entry-loop in count.rs uses `writer.write_u128::<LittleEndian>(kmer)?; writer.write_u32::<LittleEndian>(count)?;` while the canonical path uses `KmerEntry::write_to` (`write_u128::<LittleEndian>(self.kmer)?; write_u32::<LittleEndian>(self.count)`) — semantically identical, but golden proves it empirically.

`[VERIFIED: KmerEntry::write_to at format.rs:201-204]` field widths: `u128` kmer (16 bytes) + `u32` count (4 bytes) = **20 bytes per entry**. Header = 42 bytes. Magic = `b"RKDB"`. Version = `2`. All confirmed.

### Minimal delegation change

Replace `count.rs:503-532` with:
```rust
// Option A: build an RKDatabase and delegate fully
let header = DatabaseHeader {
    magic: *DATABASE_MAGIC,
    version: DATABASE_VERSION,
    kmer_size: counter.get_kmer_length() as u8,
    total_kmers: kmer_count as u64,
    sorted: sort,
    data_offset: 42,
    index_offset: 0,
    canonical: counter.canonical_mode(),
    unique_kmers: kmer_count as u64,
    file_size: 0,  // match canonical; this field is not serialized anyway
};
let db = RKDatabase { header, entries: kmers.into_iter().map(|(kmer, count)| KmerEntry::new(kmer, count)).collect(), file_path: None };
db.write_to(&mut writer)?;
```
Or the thinner Option B (delegate only the writers, keep the header struct construction in count.rs):
```rust
let header = DatabaseHeader { /* same as today but file_size: 0 */ };
header.write_to(&mut writer)?;
for (kmer, count) in &kmers {
    KmerEntry::new(*kmer, *count).write_to(&mut writer)?;
}
```
Option B is the **thinnest** change (D-09 says "thin delegation"). The header struct construction can stay in count.rs OR move to `DatabaseHeader::new` — `DatabaseHeader::new(kmer_size, total_kmers, canonical)` already exists but sets `sorted: false` hardcoded; it would need a `sorted` parameter or a builder. Recommend Option B + extending `DatabaseHeader::new` to take `sorted`, OR keep the struct literal in count.rs (it's the only call site that needs `sorted: sort`).

### Read-side `data_offset` clamp (3 sites)

`[VERIFIED: grep "data_offset"]` The defensive clamp appears in:
1. `src/database/format.rs:290-296` (`RKDatabase::from_file_path`).
2. `src/database/query.rs:79` (`DatabaseQuery::load_entries`).
3. `src/database/format.rs:173` (`DatabaseHeader::validate`) — this is the **error-reporting** site (`return Err`), not a clamp; it has different semantics.

The clamp logic at sites 1 and 2:
```rust
let actual_data_offset = if header.data_offset < 40 {
    42
} else if header.data_offset > 1000 {
    42
} else {
    header.data_offset
};
```

**What it defends against:** legacy/corrupt `.rkdb` files where `data_offset` was written with a wrong value (the comment says "Fix for incorrect data_offset in header"). The architecture docs (CLAUDE.md `## Anti-Patterns → Header data_offset reconciliation in every reader`) call this out as a code smell.

**Risk of removing it entirely:** If any existing `.rkdb` file in the wild has a bad `data_offset`, removing the clamp would cause a silent mis-seek (reading entries from the wrong offset → garbage k-mers) or a panic. **D-12 mitigates this**: the legacy sample (generated with `data_offset = 42`, the correct value) must still read after removal. **Recommendation (Claude's discretion):** replace the clamp with a one-line sanity assertion that errors loudly rather than silently rewriting:
```rust
debug_assert!(header.data_offset == 42, "expected data_offset=42, got {}", header.data_offset);
// or a hard error:
if header.data_offset != 42 {
    return Err(ProcessingError::new(format!(
        "Unsupported data_offset {} (expected 42); file may be from an incompatible rustkmer version",
        header.data_offset
    )));
}
```
This preserves the defensive intent while removing the silent-rewrite anti-pattern. **Both sites (format.rs + query.rs) must change consistently** — the duplication is the smell.

### Legacy sample generation (D-12)

Generate one `.rkdb` with the **current** code (before any read-side refactor), commit it under `tests/fixtures/legacy_v2_offset42.rkdb`, and assert the post-refactor reader loads it correctly. The sample is small (a few k-mers) — its purpose is format compatibility, not scale.

## Common Pitfalls

### Pitfall 1: `cargo build` does not enforce clippy lints
**What goes wrong:** Developer runs `cargo build`, sees no error, commits a `println!` in library code, CI fails.
**Why it happens:** `clippy::print_stdout` etc. are clippy lints (invoked by `cargo clippy`), not rustc lints (invoked by `cargo build`).
**How to avoid:** Document explicitly that the gate is `cargo clippy`. Add the crate-level `#![deny(...)]` so `cargo clippy` fails locally. Optionally add a `.cargo/config.toml` alias or a pre-commit hook running `cargo clippy`.
**Warning signs:** D-05's claim that "`cargo build` fails" — correct it to "`cargo clippy` fails" in the plan.

### Pitfall 2: CJK scan misses `println!`/`format!` string args
**What goes wrong:** The syn visitor only overrides `visit_lit`; all 51 CJK `println!` strings in `prefix_cache_merge.rs` pass the check.
**Why it happens:** `visit_lit` catches bare `Lit::Str` tokens but does NOT walk into macro argument token streams.
**How to avoid:** Override `visit_macro` AND recurse into `proc_macro2::TokenTree` (Literal + Group). Verified pattern in §1.
**Warning signs:** A CJK check that reports 0 findings in `prefix_cache_merge.rs` is broken.

### Pitfall 3: Dead pyo3 files false-positive the CJK check
**What goes wrong:** `pyo3/src/database_backup.rs` (16 CJK lines) and `database_new_approaches.rs` (13 CJK lines) trigger the check, but they're dead (not compiled).
**Why it happens:** The files are git-tracked (not gitignored) but not declared as `mod` in `lib.rs`.
**How to avoid:** Exclude `*_backup*`, `*new_approaches*`, `*.stage1_fix_backup` glob patterns in the walkdir scan. (Deleting them is out of scope per CONTEXT deferred.)
**Warning signs:** CJK check fails on pyo3 with a count much higher than the actual live-module count.

### Pitfall 4: Golden sha256 drift from `file_size` field (FALSE ALARM — verified)
**What goes wrong (initially feared):** count.rs sets `file_size = 42 + kmer_count*12`; canonical sets `file_size = 0`; delegation changes the bytes.
**Why it's a false alarm:** `[VERIFIED: format.rs:81-108]` `DatabaseHeader::write_to` does NOT serialize `file_size` or `unique_kmers` — they are in-memory-only struct fields. Both writers serialize the identical 42-byte header. The bytes match.
**How to avoid (still):** Capture golden anyway (D-10) — the entry-loop in count.rs uses raw `write_u128`/`write_u32` while canonical uses `KmerEntry::write_to`; both are LE + same widths, but golden proves it empirically.
**Warning signs:** If golden DOES drift post-refactor, the cause is an entry-encoding difference, not `file_size`. Investigate the `KmerEntry::write_to` path.

### Pitfall 5: `sha2` 0.11 API drift
**What goes wrong:** Developer bumps `sha2` to 0.11 (latest), build breaks.
**Why it happens:** 0.11 changed the `Digest` trait path.
**How to avoid:** Pin `sha2 = "0.10"` (already the case). Do NOT run `cargo update -p sha2`.

### Pitfall 6: clippy version drift across Rust versions
**What goes wrong:** Local dev (nightly 1.95) shows different warnings than CI (stable).
**Why it happens:** New clippy lints are added each release; old ones are deprecated/moved.
**How to avoid:** CI pins `dtolnay/rust-toolchain@stable` (the latest stable). Contributors on older toolchains see fewer lints. Acceptable — the constraint is "1.80+ stable". Document in the plan that CI is the source of truth for clippy.

### Pitfall 7: `data_offset` clamp removal breaks legacy files
**What goes wrong:** Removing the silent-rewrite clamp causes a real legacy `.rkdb` with a bad offset to mis-seek.
**Why it happens:** The clamp existed for a reason (legacy/corrupt files).
**How to avoid:** Per D-12, the legacy sample (generated with correct `data_offset=42`) must read. For robustness, replace the clamp with a hard error (loud failure) rather than silent acceptance — see §4 recommendation.

### Pitfall 8: `macos-latest` Python arch mismatch
**What goes wrong:** `maturin build` on macOS links the wrong Python arch or fails to find Python.
**Why it happens:** `macos-latest` is arm64; `setup-python@v5` installs an arm64 Python; `.cargo/config.toml` has empty rustflags (lets maturin handle linking).
**How to avoid:** `actions/setup-python@v5` + `pip install maturin` + `maturin build` from the `pyo3/` working directory is the canonical path. The `.cargo/config.toml` empty rustflags is intentional ("Let maturin handle Python linking automatically"). Verified locally: maturin 1.10.2 builds from pyo3/.

### Pitfall 9: `KmerEntry::read_from` endianness heuristic
**What goes wrong (latent, not phase-introduced):** `format.rs:207-229` guesses LE vs BE based on `count > 1_000_000`. A legitimate count >1M would be misread as BE.
**Why it matters for this phase:** The golden/round-trip tests should use counts ≤ 1M to avoid triggering the heuristic; OR the test should explicitly cover a >1M count to document the behavior.
**How to avoid:** Use modest counts (<1M) in golden fixtures. Note this as a pre-existing latent bug NOT in scope to fix this phase (FOUND-03 is write consolidation + data_offset, not the read endianness heuristic).
