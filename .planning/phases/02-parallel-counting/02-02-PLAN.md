<objective>
Swap the counter's storage from `RwLock<HashMap<u128,u32>>` to `dashmap::DashMap<u128,u32>` (D-04/D-05) and parallelize the per-record loop in `process_fasta_file`/`process_fastq_file` via rayon chunked `par_iter` (D-01). This delivers PCOUNT-02 (sharded concurrent counter) and the parallelism substrate for PCOUNT-04's identical-counts guarantee.

Purpose: This is the core of Phase 2. The single global `RwLock<HashMap>` serializes every increment; DashMap shards the lock so increments spread across ~4×num_cpus shards and throughput scales with core count. The parallel per-record loop is the only strategy that delivers near-core-count speedup on CRR1936095 (2 split parts → per-file parallelism would cap at ~2×). D-10 sequencing is honored: 02-04's golden baselines are already committed (this plan's depends_on=[02-04]), so any count divergence will be caught by 02-05's differential.

Output: `DashMap`-backed `KmerCounter` with atomic per-key `increment`; chunked-`par_iter` per-record loops in count.rs; D-09 default-sort flip; inline atomicity + overflow tests.
</objective>
