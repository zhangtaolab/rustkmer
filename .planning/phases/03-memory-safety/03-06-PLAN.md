<objective>
Close gap **G1** — DENSE-01 is INVERTED. The `KmerKey` enum carries a `U128(u128)` variant, so Rust gives it `u128`'s 16-byte alignment and rounds it to 32 bytes; the `(K, V)` slot the DashMap actually stores grew from 32 B to 48 B. The verifier measured **102.89 B/entry dense vs 69.34 B/entry pre-Phase-3, ratio 1.487** with 4M entries read from `/proc/self/status` — counting memory for k ≤ 32 went UP ~49% while DENSE-01 claims it roughly halves. The three assertions guarding it (`src/hash/table.rs:1018`, `tests/dense_differential_tests.rs:237,247`, `tests/dense_merge_integration_tests.rs:457`) are self-fulfilling: `key_bytes()` at `src/hash/table.rs:361` derives the width from `self.kmer_length`, never from a stored key, so the mutation "always store the wide variant" leaves all three green.

This plan makes the k ≤ 32 storage genuinely narrow (the key type carries no competing-width variant in its layout) and makes the tests observe the STORED representation rather than restate the configured `k`.

Purpose: DENSE-01 is a headline ROADMAP success criterion ("roughly halving counting memory for the common case"). It is currently measured to do the opposite. Everything else in this phase's dense story (DENSE-02 byte-identity, DENSE-03 correctness) is sound and must survive the change untouched.

Output: a `KmerCounter` whose dense table is `DashMap<u64, u32>` (16-byte slot) and whose wide table is `DashMap<u128, u32>` (32-byte slot, unchanged from pre-Phase-3), plus a test that measures real bytes-per-entry and asserts the ratio is below 1.0.
</objective>

| Boundary | Description |
|----------|-------------|
| kmer-encoded-u128 -> stored key | An encoded k-mer crosses from a `u128` at the public API into a narrower stored key. A value with bits above bit 63 would alias two distinct k-mers onto one key and silently merge their counts. |
| stored key -> on-disk `KmerEntry` | A `u64` key widens back to `u128` for the `.rkdb` write path. A non-zero-extending widening changes every v2 byte. |
