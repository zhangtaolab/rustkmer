<objective>
Close code-review finding **WR-04** (the escalated form of a deferred item), finding **WR-08**, and the remaining half of the recorded streaming-chunk sweep gap. The verifier judged the prefix-cache partial-merge defect "worse than recorded" and said it should not survive into a release that claims bounded merges.

Three specific defects, all in `src/database/prefix_cache_merge.rs`:

- **Recovery path destroyed (WR-04 aggravator 1).** Lines :399-408 deliberately moved shard deletion off the success branch so it also runs on failure ("this is only a peak-disk optimization, so it runs on the failure path too"). For a FAILED bucket that deletes the bucket's shard files *before* the error is swallowed at :485. There is no longer any on-disk artifact from which the lost k-mers could be recovered or the bucket retried. Phase 3 improved peak-disk behaviour and, in the same edit, closed the last recovery path for the silent-loss case.
- **Errors swallowed (the original deferred item).** `merge_prefix_buckets` logs per-bucket failures and returns `Ok(())` regardless, so `concatenate_final_output` writes a partial `.rkdb` whose `total_kmers` header reflects only the buckets that happened to succeed.
- **The integrity check is a tautology (WR-04 aggravator 2).** Lines :871-874 compare `total_kmers` (= `data_size / RECORD_SIZE`, where `data_size` sums the buffers of the merged bucket files) against `total_kmers_in_files` (sums `file_size / RECORD_SIZE` over those SAME merged bucket files). The two are computed from identical inputs, so the comparison can never differ, and it cannot even see a zero-length bucket because that bucket is `continue`d at :821-825 and contributes to both sides equally. A check named "Possible duplicates or loss" that cannot detect loss is worse than no check. Note also that the obvious replacements are not fixes: re-deriving the bucket count from the merged file's size is the same tautology, and comparing against the input shard sizes would exceed the merged count on every merge with an overlapping k-mer (`merge_single_prefix_hashmap` dedups through `HashMap<u128, u32>`), so an `Err`-on-mismatch version would fail ordinary merges.

Plus **WR-08**: `concatenate_final_output` reads each merged bucket wholly into RAM with `read_to_end` (:831-832) before appending, so the path advertised as memory-efficient peaks at the size of the largest single bucket. And the recorded sweep gap: `sweep_stale_merge_dirs` (`src/database/temp_lifecycle.rs:125`) selects on `rustkmer-merge-*` DIRECTORIES only, so a streaming merge killed by SIGKILL or `panic = "abort"` (this project's release profile) leaves `rustkmer_sort_*.chunk` files loose in `temp_dir` that nothing ever reclaims.

Purpose: MERGE-01 promises human-scale merges no longer OOM the process, and MERGE-03 promises failed merges do not exhaust the disk. A merge that silently loses k-mers and reports success undermines both — and this phase made the prefix-cache path's cleanup stricter while leaving its failure handling as permissive as before.

Output: a failed bucket aborts the merge with a loud `Err` and leaves its shards recoverable, an integrity check that can actually fire, a block-copy concatenation, and a sweep that reclaims loose chunks.
</objective>
