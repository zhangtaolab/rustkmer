<objective>
Add RAII temp-file guards to the prefix-cache merge path, route all merge temp shards under a process-unique subdir, and add a startup stale-shard sweep (D-06).

Purpose: MERGE-03 ("failed/interrupted streaming merges clean up temporary shard files — no silent disk exhaustion") is currently unmet on the prefix-cache path: `prefix_cache_merge.rs:322-326` only `remove_file`s shards on the success branch, so panic / early `?` return / `kill -9` / power loss leaks them. The streaming path already has RAII (`streaming_merge.rs::TempFileManager::Drop` + `StreamingMergeIterator::Drop`) — this plan mirrors that pattern onto the prefix-cache path, promotes `tempfile` from `[dev-dependencies]` to `[dependencies]` so `tempfile::TempDir` can be used in production, and adds the `sweep_stale_merge_dirs` defense that runs on merge start (because `panic="abort"` in the release profile means `Drop` does NOT run on abort/SIGKILL — the sweep is the real defense against `kill -9`/power loss, per 03-RESEARCH.md Pitfall 2 / Pattern 3).

Output: A merge subsystem where every temp shard lives under a process-unique `rustkmer-merge-*` subdir, RAII cleans up on normal/panic-unwind exit, and the startup sweep cleans up orphans from abort/SIGKILL/power-loss — closing the disk-exhaustion DoS vector and the CONCERNS.md "Streaming-merge error paths untested / partial-failure cleanup" test gap.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `std::env::temp_dir()` → merge temp subdir | Shared with other processes/users on the machine. Process-unique naming (`rand_bytes(8)`) + `tempfile`'s `O_CREAT|O_EXCL` semantics prevent symlink/TOCTOU and collision attacks. |
| Stale `rustkmer-merge-*` dirs in temp_dir → sweep | The sweep removes dirs by prefix match + mtime TTL. A non-rustkmer process's `rustkmer-merge-*`-named dir could be wrongly swept — mitigated by the conservative 7-day TTL and the fact that only rustkmer writes this prefix. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-04 | Tampering | Temp-file symlink TOCTOU on prefix-cache shards | medium | mitigate | `tempfile::Builder::new().prefix("rustkmer-merge-").rand_bytes(8).tempdir_in(...)` uses `O_CREAT\|O_EXCL` (or `O_TMPFILE` on Linux) — the file cannot be pre-existing, defeating the classic temp-file race. ASVS V12 standard control. `[CITED: docs.rs/tempfile]` |
| T-03-05 | Denial of Service | Disk exhaustion from orphaned shards (kill -9 / panic=abort / power loss) | high | mitigate | Process-unique subdir + startup sweep (D-06). The `rustkmer-merge-` prefix enables unambiguous identification. 7-day TTL is generous (merges complete in hours). This IS the MERGE-03 mitigation. Covered by `orphan_subdir_swept_on_next_start` test. |
| T-03-06 | Tampering | Cross-process merge collision (two merges write the same shard path) | medium | mitigate | Process-unique subdir via `rand_bytes(8)` — collision probability is negligible (8 bytes = 2^64 namespace). Covered by `two_concurrent_merges_do_not_collide` test. |
| T-03-07 | Tampering | Sweep wrongly removes a non-rustkmer dir | low | accept | Only the `rustkmer-merge-` prefix is swept; another tool using the exact same prefix would be swept, but the prefix is rustkmer-specific. 7-day TTL prevents removing in-flight merges. Acceptable for ASVS L1. |
| T-03-08 | Elevation of Privilege | Temp file permissions (other users read merge data) | low | mitigate | `tempfile` creates files with `0600` perms by default (creator-only) on Unix. The merge data (k-mer counts) is not sensitive but defense-in-depth via default perms is free. |
| T-03-SC | Tampering | `tempfile` package (promoted dev→dep) | high | mitigate | `tempfile` passed the package-legitimacy gate in 03-RESEARCH.md §"Package Legitimacy Audit" (OK verdict, ~11 yrs old, 11.3M weekly downloads, Stebalien/tempfile). Promotion does not change the version (3.12 declared, 3.24.0 resolved). No blocking checkpoint needed (verdict is OK, not ASSUMED/SUS). |
</threat_model>
