<objective>
Close CR-01 / the open WR-03 root cause (mixed-canonical prefix-cache correctness debt) per the user's 2026-10-09 triage of 03-VERIFICATION.md human decision item 1: fix in-phase via this third gap-closure round rather than accept as advisory.

The defect: in src/database/prefix_cache_merge.rs split_files_by_prefix, each record's bucket is chosen from processed_kmer (canonicalized via canonical_kmer_u128 when ANY input is canonical) but the shard stores the RAW entry.kmer. On the opt-in mixed-canonical capability (any canonical + any non-canonical input under use_prefix_cache), bucket order does not equal raw-key order, so concatenate_final_output can emit non-ascending output under a sorted: true header — binary-search consumers (query_kmer, extract_prefix_optimized) silently return wrong results on that subset. The same raw-write makes that subset content-wrong: un-summed duplicate encodings (raw and canonical forms of the same k-mer written as separate records instead of summed).

The fix is one site: write processed_kmer to the shard (the same canonicalization decision already used for bucketing) and propagate canonicalization errors instead of the swallowed fallback. That closes content (duplicates summed by the 03-13 bucket writers once both encodings land in one bucket), header semantics (the output genuinely IS canonical, matching the ANY-input flag), and output order (bucket key == stored key restores the 03-15 construction argument) at once.

Output: fixed src/database/prefix_cache_merge.rs, a RED-provable mixed-canonical order/conservation/query test, a corrected ANY-canonical header pin in the routing tests.
