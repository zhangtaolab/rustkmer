<objective>
Close the **header half of gap G2** (= code-review finding CR-02) plus findings **WR-01**, **WR-06**, **IN-01**, and deferred item **(b)**. D-01 correctly diagnosed that "the function whose whole job is to prevent OOM was itself the OOM" and fixed the ESTIMATOR — but the same `from_file_path` materialization survives unaltered in the three strategies the estimator routes into:

- `merge_databases_streaming` (`src/database/format.rs:852`) loads `input_paths[0]` in full purely to read `kmer_size` and `canonical` — on the path chosen precisely when the inputs do not fit.
- `merge_databases_prefix_cache` (`:1048-1052`) holds every input as a live `RKDatabase` through the final `from_file_path(&temp_output)` at `:1078`, so peak is all-inputs-plus-full-output.
- `ExternalSortMerger::new` (`src/database/prefix_cache_merge.rs:76`, `:82-86`) loads every input a second time, and uses the first one only for its header.

Alongside them, WR-01: `estimated_memory = total_kmers * 24` models roughly a quarter of the peak it is meant to bound, so a merge the gate admits can still OOM. And IN-01: `merge_buffer_mb.max(1024)` silently overrides a smaller `--max-memory` on the prefix-cache path.

Purpose: admission control is only meaningful if the thing it admits is bounded, and it is only calibrated if the constant is right. This plan makes every route's inputs header-only and charges each route its real peak. The substantive half of CR-02 — streaming the merged output instead of accumulating it — is plan 03-10, which depends on this one.

Output: no merge route materializes an input database it does not need to, the per-route admission model reflects the peak each route actually reaches, and `merge_databases(&[], ..)` errors instead of panicking.
</objective>
