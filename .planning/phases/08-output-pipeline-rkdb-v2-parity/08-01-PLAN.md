<objective>
Make the CLI's counting-output stage fast without changing a single output byte, and record the pre-change baseline that proves the drop.

Purpose: Phase 7 proved the output stage now dominates the slice wall (count phase ~6.5 s at t4; slice wall 17.76 s), and the CLI still sorts 229M pairs with a single-threaded stable sort — and, for text output, with a decoded `String` allocated on every comparison. OUT-01 requires the sort to be unstable/parallel, the write to stream from that one sorted buffer into the frozen `format.rs` writers, and the text order to be numeric. This plan captures the pre-change numbers first (a state that cannot be re-created after the refactor), then lands the sorted `.rkdb` path and the text path, each proven byte-identical to the pre-refactor output.

The streaming shape chosen here is the sorted-slice shape the phase context allows: the pair buffer is the ONE sort buffer (the in-place parallel unstable sort), each partition table is released as it drains into that buffer, and the writer emits one record at a time from it through the frozen header/entry codec. There is therefore never a second full entry copy (the `RKDatabase::from_kmer_pairs` entries-Vec shape) and the extra resident set is bounded by the pair buffer alone, with the drained tables released behind it — so peak RSS cannot exceed the pre-change peak that held every table plus the same buffer. The alternative pull-iterator shape (a k-way merge of per-partition sorted runs) is deliberately not built: it adds merge machinery and ordering risk for a memory win the RSS gate already bounds.

The phase context cites a ~13.4 s single-threaded stable sort on 229M keys. That figure is treated as an upper-bound reference, not a target: the capture in Task 1 measures the actual sort-attributed delta on this host (an ad-hoc pre-check measured ~7.7 s inside the pipeline), and the measured number governs the post-change comparison.

Output: a consuming pair collector, a shared parallel unstable sort, two streaming writers taking ownership of the result, a standing output-stage measurement gate with unit tests, an integration test file, and the immutable pre-change baseline document.

Task order note: the measurement-only baseline task runs before the tracer because the pre-change state it measures cannot be re-created once the tracer lands (re-measuring afterwards would produce a post-change baseline and void the OUT-01 claim). The tracer is the plan's first code-producing task and carries the end-to-end byte-identity proof.
</objective>
