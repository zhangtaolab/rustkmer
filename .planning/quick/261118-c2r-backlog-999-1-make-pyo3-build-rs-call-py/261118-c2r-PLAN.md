<objective>
Make `pyo3/build.rs` emit the macOS extension-module link args by calling
`pyo3_build_config::add_extension_module_link_args()`, re-add
`pyo3-build-config = "0.27.2"` as a `[build-dependencies]` entry, refresh

Purpose: close backlog 999.1 (Phase 03 UAT Test 22). pyo3 0.27 no longer
auto-emits `-undefined dynamic_lookup`, so at HEAD a macOS extension-module
build fails at link time unless the user injects RUSTFLAGS by hand; the
documented manual-build recipe is therefore broken as written.
Output: 2 atomic commits (build wiring + lockfile; docs correction), with the
link behavior proven end-to-end without any RUSTFLAGS export.

Planning shape note: one leaf build-config change plus record-only docs edits.
No new runtime layer, API, or persisted format is involved; the change is
proven end-to-end by a real link gate, so a tracer slice would add no
information (the --no-tracer condition).

Decision (gating, recorded per task constraints): call
`add_extension_module_link_args()` UNCONDITIONALLY, not behind the crate's
`extension-module` cargo feature. Rationale: (1) the function itself does not
consult the feature — pyo3-build-config 0.27.2 emits the Darwin flags
unconditionally and is a no-op elsewhere; (2) `rustc-cdylib-link-arg` applies
only to this crate's cdylib link step, so it cannot affect tests, bins, or
consumers; (3) the documented manual build (docs/guides/pyo3-binding-readme.md
section 1) runs plain `cargo build` without `--features extension-module`, so
gating on `CARGO_FEATURE_EXTENSION_MODULE` would leave exactly the documented
path the backlog targets unfixed; (4) PyO3's documented build-script pattern
is the unconditional call. Do NOT add `pyo3_build_config::use_pyo3_cfgs()` —
no `cfg(Py_*)` usage exists in pyo3/src, and it is out of scope.
