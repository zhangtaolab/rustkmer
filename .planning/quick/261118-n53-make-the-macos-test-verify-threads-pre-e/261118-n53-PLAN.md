<objective>
Make the macOS `test_verify_threads.py::TestNegativeControls::test_pre_engine_n_plus_one_stub_is_measured_red` negative control deterministic by hardening `observe()` against late-sample clobbering, pin the new behavior with deterministic unit tests, stress-verify the negative control, and close the stale ~50% flake records.

Purpose: `_thread_count` (261118-bhr) retries a zero-thread `sample` report, but `observe()` still records `last_observed = count` on every successful sample. On the undershoot path (negative control expects 9, the stub holds 5) the loop only exits when the child dies, and the final `sample <pid> 1` window starts ~5.9 s into a child that calls `os._exit` at ~6.05 s. A truncated late report with a NONZERO smaller count (e.g. 3) therefore overwrites a correct 5 even after the zero-case fix. A counting child's OS thread set is monotonically non-decreasing before exit (persistent engine + rayon pools), and a truncated sample can only under-count, so the peak nonzero observation is the correct measurement. The orchestrator confirmed the race shape with a scratch probe at planning time: HEAD's `observe()` returns 3 for the scripted `[5, 5, 3]` sequence and 2 for `[5, None, 2, None]`; the peak guard returns 5 for both, while the existing intermediate `[5, 9]` and constant-`[5, 5, 5]` contracts stay 9 and 5. Decision: hardening `observe()` alone suffices and the stub needs NO behavioral change — the race is structural on the observer side (`sample <pid> 1` always spans a ~1 s window and the helper's final poll necessarily crosses the stub's exit; `os._exit` already avoids the daemon-teardown window, so no stub exit style can stop a sampling window from crossing process death), and a stub-only change would leave real counting children exposed. Only the stub's explanatory comment is updated.

Output: 2 atomic commits — the helper/test fix, then the record closure — plus a summary recording the RED proof values, the 22-test run, and the 10/10 stress result.
