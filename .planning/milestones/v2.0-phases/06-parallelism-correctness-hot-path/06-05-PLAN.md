<objective>
Close the single Phase 6 blocker: the aggregate `total_kmers` statistic silently loses updates when `reduce_local_counts` merges drained locals concurrently, because `merge_local_counts` publishes the shared `AtomicU64` with a non-atomic load + checked_add + store while its callers run under `locals.par_iter().try_for_each` (src/hash/table.rs:469-481 publishing, 524-531 concurrent callers, contradicting the doc claim at 499-500). Per-key u32 counts and `.rkdb`/text output are already exact; the defect is the user-visible aggregate reported by the CLI "Total k-mers" line and `PyCounter.get_stats().total_kmers`.

Purpose: Restore the PAR-02 truth that `total_kmers`, `unique_kmers`, and filtering statistics keep their existing semantics under the parallel reduction introduced by 06-04, without giving back the scaling win (per-key merges must stay parallel) and without weakening the checked fail-loud overflow contract or any exact-count guarantee.

Output: An atomic read-modify-write publication of `total_kmers` that composes concurrent merge deltas, a deterministic regression test that reproducibly fails on the pre-fix tree and passes after, and updated documentation that states the real concurrency contract.
</objective>

Implementation:
- Call self.total_kmers.fetch_update(Ordering::Relaxed, Ordering::Relaxed, |current| current.checked_add(merged_total)). fetch_update internally retries the closure with the freshly observed value on concurrent modification, which is the compare-exchange loop this gap requires. - On Ok, publish merged_unique with the existing fetch_add(merged_unique, Relaxed) and return Ok.
