<objective>
Remove the hardcoded `num_threads = 1` single-thread restriction from the `count` command and plumb a proper thread-count resolution chain through the CLI (per D-06, D-07 — implements PCOUNT-01).

Purpose: This is the prerequisite for Phase 2's parallel counting. Without configurable threads, the dashmap swap in 02-02 and the GIL release in 02-03 would have no effect — counting would still run single-threaded. This plan delivers the user-facing knob (`--threads`), the env-var layer (`RUSTKMER_THREADS`), and the precedence chain, AND fixes a latent landmine in `merge.rs` (Pitfall 3) so the parallel count path cannot crash a subsequent merge.

Output: `--threads` CLI flag on `count`; `resolve_thread_count` helper; centralized `build_global()` (Err-tolerant) in `execute_count`; `merge.rs` `.expect()` replaced with Err-tolerant logging.
</objective>

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-01 | Tampering | `resolve_thread_count` env-var parsing | low | mitigate | Parse via `str::parse::<usize>()` and reject `t < 1` (the validation already in Task 1's action); a malformed value falls through to the next precedence tier rather than panicking. No `unwrap()` on env input. |
| T-02-02 | Denial of Service | `build_global` second-call panic in merge (Pitfall 3) | high | mitigate | Task 2 replaces both `.expect()` sites in merge.rs with Err-tolerant logging — a count→merge workflow can no longer panic the process. | T-02-03 | Denial of Service | unbounded `--threads` value (e.g. `--threads 999999`) | low | accept | Rayon's ThreadPoolBuilder clamps/ignores absurd values gracefully (spawns up to num_cpus); the value is also bounded by the OS thread limit. Not worth a custom cap — Phase 4 benchmark will surface pathological settings. |
