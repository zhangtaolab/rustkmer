<objective>
Close gap **CR-01 (+WR-03)** (03-VERIFICATION.md gaps[1]): the prefix-cache route's per-bucket streaming reader corrupts and loses records for shards above one ~4 MB batch.

`read_batch_from_file_sync` (prefix_cache_merge.rs:937-968) clears its buffer at every call (`data.clear()` at :942), reads 8192-byte chunks until `bytes_read >= 4_000_000` (so it consumes 4,005,888 bytes — 489 x 8192; 4,005,888 mod 20 = 8), drops the trailing 8 partial-record bytes, and leaves the BufReader 8 bytes mid-record — so EVERY subsequent record in that shard parses from a shifted offset. `Err(_) => break` (:954) swallows real IO errors as end-of-batch. Separately (WR-03), the peek-and-add branches at :886-887 and :897-899 consume a within-file duplicate by adding its count but neither remove it nor push a heap entry for its file — the rest of that file's run is silently stranded. The 03-11 integrity checks cannot see either defect (both sides derive from the same corrupted stream). Reachable via `use_prefix_cache` with the streaming bucket strategy whenever a shard exceeds ~4 MB — routine at exactly the human scale this phase targets.

Purpose: MERGE-01/MERGE-03 integrity — a partial or corrupt `.rkdb` must never be concatenated and reported as a successful merge (03-11's own guarantee, defeated by this reader).

Output: a record-aligned, error-propagating batch reader; an unstranding k-way merge; and conservation proofs at >4 MB scale that are red on the current tree.
</objective>
