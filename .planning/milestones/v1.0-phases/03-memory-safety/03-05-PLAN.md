<objective>
Expose `max_memory` and `merge_mode` keyword arguments on `pyrustkmer.PyDatabase.merge`, routing Python users through the same bounded merge core as the CLI (MERGE-04).

Purpose: MERGE-04 ("`pyrustkmer`'s `PyDatabase` merge uses the same bounded path as the CLI") requires the PyO3 binding to (a) accept budget/strategy kwargs mirroring `--max-memory` / `--merge-mode`, (b) validate them at the Python boundary (the PyCounter `threads=` analog), and (c) build a `MergeConfig` and call `RKDatabase::merge_databases` — which, after plan 03-01 lands, is the bounded dispatcher with the D-01 header-only estimator and D-02 reject branch. Because the dual-surface shared-core design (ARCHITECTURE) means `PyDatabase::merge` already calls `RKDatabase::merge_databases`, the D-01/D-02 fixes inherit automatically; this plan is purely additive param-threading, not reimplementation. The current site at `pyo3/src/database.rs:1346-1392` uses `MergeConfig::default()` with no params exposed — that is the gap.

Output: A `PyDatabase.merge(databases, output, *, max_memory=None, merge_mode='auto')` signature where Python users get the same budget control as CLI users, invalid `merge_mode` values raise `PyValueError`, over-budget explicit-`memory` requests surface the D-02 reject as a Python exception, and the streaming path is selectable for human-scale merges from Python.
</objective>

| PyDatabase.merge -> RKDatabase::merge_databases | Same core path as CLI; the 03-01 estimator + D-02 reject apply. No new trust boundary — Python inherits the bounded dispatch. |
