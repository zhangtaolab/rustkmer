<objective>
Swap the in-memory k-mer counter key from `u128` to a width-selected `KmerKey` enum (`U64(u64)` for k ≤ 32, `U128(u128)` for 33..=64), roughly halving counting memory for the common case, while preserving the `.rkdb` v2 on-disk format byte-for-byte and keeping the public API identical (D-03, DENSE-01/02/03).

Purpose: DENSE-01 ("k ≤ 32 stored as u64 instead of u128 — roughly halving counting memory") requires the `DashMap` key to narrow for the common case. DENSE-02 ("transparent to existing readers — v2 backward/forward compatible") is satisfied trivially by D-03's RAM-only rule: `KmerEntry` on disk stays 16-byte u128 + 4-byte u32, and the write path zero-extends `u64 -> u128`. DENSE-03 ("canonicalization stays correct under u64 packing") is verified at the **decoded (kmer-string, count) level** — NOT raw-integer equality, because `encode_kmer_bytes` aligns to bit 64 while `encode_kmer_bytes_u128` aligns to bit 128 (D-04). The 12 Phase 1/2 golden `.rkdb` + sha256 baselines are ground truth; no re-capture (Phase 1 D-10 carry-forward).

Output: A `KmerCounter` whose internal storage is `DashMap<KmerKey, u32>` (width-selected at construction), whose public surface is unchanged, whose write path produces byte-identical v2 `.rkdb` files, and whose u64 path is proven equal to the u128 path at the decoded level across the D-13 matrix + random proptest inputs.
</objective>
