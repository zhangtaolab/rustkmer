<objective>
Close the **substantive half of gap G2** (= code-review finding CR-02). Plan 03-09 removed the input materialization; this plan removes the OUTPUT materialization, which is the reason "streaming" was not a memory escape at all.

`merge_databases_streaming` (`src/database/format.rs:838-892`) drains the whole merged stream into `sorted_kmers: Vec<(u128, u32)>` (:869-877) and then calls `from_kmer_pairs` (:891), which builds a THIRD full copy as a `Vec<KmerEntry>`. The caller then writes that to disk. So the route chosen precisely because the inputs do not fit holds roughly 2-3x the entire dataset at peak — strictly worse than the in-memory path it replaced. The prefix-cache path has the same shape: `merge_databases_prefix_cache` writes a complete `.rkdb` to `temp_output` and then immediately reads it back with `from_file_path` (:1078) to return it as an `RKDatabase`.

The reason is the API: `merge_databases` returns an `RKDatabase`, and `RKDatabase` owns a `Vec<KmerEntry>`. Both shipped front-ends (`src/cli/commands/merge.rs:447-454` and `pyo3/src/database.rs:1443-1457`) do exactly the same thing — merge into RAM, then write the file — so a streaming merge is followed by a full materialization regardless of the route.

Purpose: MERGE-01's promise is that human-scale merges no longer OOM the process. A merge that streams its inputs and then materializes its output has not delivered that. This plan adds a path-shaped entry point, makes the streaming route write its output incrementally, and turns the prefix-cache handoff into an O(1) rename — then points both front-ends at it.

Output: `RKDatabase::merge_databases_to_path`, a streaming writer that emits `.rkdb` bytes as the merge yields them, and a CLI + Python that use them. `merge_databases` remains as a library-compatibility shim that materializes, documented as such.
</objective>
