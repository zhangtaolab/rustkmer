<objective>
Close gap **CR-02** (03-VERIFICATION.md gaps[2]): the prefix-cache route's output claims `sorted: true` but is (low_byte, kmer)-ordered. `get_prefix_4mer` (prefix_cache_merge.rs:970-973) returns `kmer & 0xFF` — the LOW byte of the right-aligned encoding (the LAST 4 bases) — while `concatenate_final_output` loops buckets in index order 0..255 (:1010) and each bucket is internally ascending, so the output is ordered by (low_byte, kmer): k-mer 0x100 (bucket 0) is written before k-mer 0xFF (bucket 255), violating ascending u128 order — yet the header is written `sorted: true` (:1175). Every consumer that trusts the flag silently breaks: `query_kmer` switches to binary search on the flag (format.rs:591-596), `prefix_query_optimized` binary-searches sorted databases (:86-120, :264-310) — exact-match queries return None or a wrong count. Untested on this route (route tests assert header.sorted only for in-memory/streaming; the one unit test naming prefix extraction, IN-07, never calls the function).

Fix option (a) per the review: bucket by the HIGH 8 bits (the true first 4 bases) so index-order concatenation is globally ascending and the existing `sorted: true` becomes TRUE. Options (b) (`sorted: false`) and (c) (sort at concatenation) are rejected — (b) degrades prefix extraction to linear scans and breaks the phase's sorted-output contract, (c) re-reads and re-sorts the whole dataset the route exists to avoid touching.

Purpose: MERGE-01 correctness + DENSE-02's "queryable output" half — a merged database must answer queries correctly regardless of the route that produced it.

Output: first-4-bases bucketing, a truthful sorted flag, a real unit test for the bucketing function, and end-to-end query proofs that are red on the current tree.
