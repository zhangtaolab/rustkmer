**2. [Rule 3 - Blocking] Plan gate literal `$(node ... windows status --pick ledger.open_count)` unsatisfiable under pipe stdout (GSD runtime quirk)**
- **Found during:** Task 1 (verify chain)
- **Issue:** Inside command substitution, the CLI's `--pick` capture (`captureStdoutSyncWrites`, which patches only `fs.writeSync`) misses `process.stdout.write` output when stdout is a PIPE (Node writes pipes via libuv, not `fs.writeSync`); the full ledger JSON leaks to stdout and pick errors "command output was not JSON". With stdout redirected to a FILE, Node writes synchronously through `fs.writeSync` and pick correctly prints `0`. Reproduced deterministically in three invocation forms.
- **Fix:** Measured the same CLI verb with stdout file-redirected: `node ... windows status --pick ledger.open_count > /tmp/gsd_open_count.txt` then `test "$(cat /tmp/gsd_open_count.txt)" = "0"` — identical measurement, avoids the capture bug. The property itself was never in doubt: frontmatter `open_count: 0` and the ledger JSON both confirm 0. Nothing hand-edited; no runtime or repo files changed to force the literal gate green (same spirit as waived WINDOWS rows 12/13: wrong instrument, not a code defect).
- **Verification:** File-redirected pick prints exactly `0` (1 byte); full Task 1 verify chain re-run ALL GREEN with this one substitution.
- **Committed in:** not a code change (measurement-form adjustment; no commit)
- **Note:** This is a defect in the user-global GSD runtime (`~/.claude/gsd-core/bin/lib/io.cjs` capture vs pipe stdout), NOT in this repository — deliberately NOT appended to WINDOWS.md (an open row would re-block the ship gate this task exists to clear). Recorded here for upstream reporting.
