# Phase 0 Research: Comprehensive RustKmer CLI Testing

## 研究发现与决策

### 1. 测试数据验证

**决策**: 使用 /Users/forrest/Temp/demodata 中现有的基因组数据文件进行测试

**理由**:
- 用户明确指定使用现有数据
- 避免下载大型基准数据集的时间消耗
- 真实项目场景通常使用已有数据

**已验证的文件类型**:
- FASTA 格式基因组序列文件
- FASTQ 格式测序数据文件
- 不同大小的文件用于测试不同场景

### 2. 性能基准测试策略

**决策**: 使用 Rust 的 criterion 框架进行性能基准测试

**理由**:
- criterion 是 Rust 生态系统中最成熟的基准测试库
- 支持统计分析，可以检测性能回归
- 与现有依赖栈兼容
- 能够生成详细的性能报告

**替代方案考虑**:
- 自定义计时脚本：功能有限，缺乏统计分析
- hyperfine：跨语言工具，但与 Rust 生态系统集成度不高

### 3. 内存监控方案

**决策**: 使用系统调用和 /proc/self/status 进行内存使用监控

**理由**:
- 跨平台兼容（Linux/macOS）
- 提供详细的内存使用信息（RSS, VMS等）
- 轻量级，不影响被测试程序的性能

**实现方式**:
- 在测试脚本中集成内存监控命令
- 定期采样内存使用情况
- 记录峰值内存使用

### 4. 测试报告格式

**决策**: 使用 Markdown 格式生成测试报告，包含：
- 测试环境信息
- 测试步骤和命令
- 结果表格和图表
- 性能指标
- 发现的问题和建议

**理由**:
- 易于阅读和版本控制
- 支持代码块和表格
- 可以转换为其他格式（PDF, HTML）
- 符合技术文档标准

### 5. 并行测试策略

**决策**: 对于支持并行处理的命令（如 count），测试不同的线程数

**测试维度**:
- 单线程性能
- 多线程扩展性（2, 4, 8 线程）
- 内存使用与线程数的关系
- 是否有线程数量的上限

### 6. 错误处理测试场景

**测试用例设计**:
- 无效的输入文件路径
- 损坏的 FASTA/FASTQ 文件
- 权限不足的输出目录
- 磁盘空间不足
- 不兼容的数据库格式

### 7. 模糊查询验证方法

**决策**: 使用已知序列和预先计算的 Hamming 距离进行验证

**验证步骤**:
1. 选择参考 k-mer
2. 生成所有指定距离内的变异序列
3. 验证查询结果是否包含所有预期的 k-mer
4. 检查结果中是否包含不应该返回的 k-mer

### 8. 测试自动化脚本

**技术选择**: 使用 Bash 脚本配合 Rust 测试二进制文件

**优势**:
- 易于修改和扩展
- 可以直接调用 rustkmer 命令
- 支持复杂的测试逻辑
- 生成结构化的报告

### 9. 版本兼容性考虑

**决策**: 记录测试时使用的 rustkmer 版本和编译信息

**包含信息**:
- Rust 版本
- rustkmer git commit hash
- 编译时间和优化级别
- 系统环境信息
